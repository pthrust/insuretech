# Переход на Event-Driven архитектуру 

# Анализ текущей архитектуры InsureTech: проблемы и риски

## 1. Контекст

Сейчас взаимодействие между сервисами построено на синхронных REST-вызовах:

- `core-app` → `ins-product-aggregator` каждые 15 минут (получение каталога продуктов).
- `ins-comp-settlement` → `ins-product-aggregator` раз в сутки (реестр оформленных страховок).
- `ins-comp-settlement` → `core-app` раз в сутки (получение оформленных за день страховок).
- `ins-product-aggregator` → 5 страховых компаний (синхронно, в рамках одного HTTP-запроса).

Дополнительно `core-app` и `ins-comp-settlement` хранят локальные реплики каталога
продуктов и тарифов, чтобы не дёргать aggregator на каждый запрос пользователя.

## 2. Проблемы текущей архитектуры

### 2.1. Синхронный fan-out в aggregator

`ins-product-aggregator` в момент вызова:
1. Синхронно обращается ко всем 5 страховым компаниям.
2. Агрегирует ответы.
3. Возвращает результат в рамках того же HTTP-запроса.

Последствия:
- **Время ответа = max(время ответа всех партнёров)**, а не среднее.
- Если один партнёр тормозит — тормозит весь aggregator.
- Ошибка 5xx у одного партнёра ломает весь вызов, хотя остальные 4 могли ответить.
- Нет graceful degradation: частичный каталог вернуть нельзя.

### 2.2. Каскадные отказы (cascading failures)

`core-app` вызывает aggregator каждые 15 минут и ждёт ответа. Если aggregator
завис — запросы core-app накапливаются, исчерпывается пул потоков, падают
пользовательские запросы.

### 2.3. Жёсткая связность (tight coupling)

- `core-app` знает про REST API aggregator.
- `ins-comp-settlement` знает про REST API и aggregator, и core-app.
- Добавление 5 новых страховых компаний = доработка aggregator + пересборка
  каталога + рост времени ответа.

### 2.4. Синхронные суточные вызовы

`ins-comp-settlement` раз в сутки:
- синхронно тянет каталог из aggregator;
- синхронно тянет оформленные страховки из core-app.

Если любой из этих сервисов в момент вызова недоступен — расчёты со страховыми
компаниями срываются, выплаты агентских премий задерживаются.

### 2.5. Дублирование данных без гарантий согласованности

`core-app` и `ins-comp-settlement` держат локальные реплики каталога.
Источник истины — aggregator, но синхронизация происходит по расписанию,
а не по событиям. Данные могут расходиться:
- core-app обновился, settlement — ещё нет;
- между обновлениями партнёр изменил тариф — оба сервиса работают со старой ценой.

### 2.6. Отсутствие идемпотентности и повторных попыток

При таймауте REST-вызова нет гарантии, что операция не выполнилась на стороне
получателя. Нет механизма повторной доставки. Нет DLQ (dead letter queue).

## 3. Риски при росте нагрузки

| Риск | Причина | Влияние |
|---|---|---|
| Рост времени ответа aggregator | +5 страховых компаний → +100% параллельных вызовов в одном запросе | Пользователи ждут, NPS падает |
| Рост количества ошибок API | Больше партнёров = больше отказов | Ломается каталог, оформление заявок |
| Перегрузка core-app | Синхронные вызовы aggregator каждые 15 мин + рост трафика | Каскадный отказ |
| Срыв суточных расчётов | 10 партнёров → дольше собирается реестр | Задержка выплат, штрафы по SLA |
| Рассинхрон каталогов | Периодическая синхронизация не успевает | Продажа по устаревшим тарифам |
| Невозможность масштабировать aggregator | Fan-out в одном запросе ограничивает горизонтальное масштабирование | Единственная точка отказа |
| Сложность добавления партнёра | Требуется доработка aggregator и пересборка каталога | Долгий time-to-market |

## 4. Подход для решения проблемы

Архитектуру нужно перевести с синхронного request-response на **Event-Streaming**:

- `ins-product-aggregator` публикует события обновления каталога;
- `core-app` и `ins-comp-settlement` подписываются на них и обновляют локальные реплики;
- `core-app` публикует события о новых оформленных страховках;
- `ins-comp-settlement` подписывается и получает данные асинхронно.

Это устранит каскадные отказы, снизит связность, обеспечит eventual consistency
и позволит масштабировать систему до 10+ страховых компаний.
