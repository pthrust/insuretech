# Архитектурное описание: OSAGO Aggregator

## 1. Реализация osago-aggregator
Для сервиса необходимо **собственное хранилище**. Причины для этого:
* **Высокая нагрузка:** 2 500 одновременных пользователей × 5–10 страховых компаний = до **25 000 одновременных исходящих запросов**.
* **Длительное время ожидания:** Каждая страховая может отвечать до 60 секунд. Состояние заявки «живёт» долго, поэтому система должна без потерь переживать рестарт пода (контейнера).
* **Специфика опроса (polling):** Требует обязательного хранения `external_id` от страховой, текущего статуса, числа попыток и времени следующего опроса.
* **Идемпотентность:** Гарантия того, что одна и та же заявка не будет отправлена дважды.
* **Отказоустойчивость:** Паттерны *Retry* и *Circuit Breaker* (по каждому иншуреру) требуют постоянного учёта и ведения статистики.

### Схема osago-db (PostgreSQL)
```sql
-- Таблица заявок пользователей
osago_application (
    id, 
    user_id, 
    car_data, 
    status, 
    created_at, 
    ttl_at
)

-- Таблица запросов в страховые компании
insurer_request (
    id, 
    application_id, 
    insurer_id, 
    external_id, 
    status, 
    response, 
    attempts, 
    next_poll_at, 
    timeout_at, 
    event_id UNIQUE
)

-- Таблица для реализации паттерна Transactional Outbox
outbox
```

### API osago-aggregator для core-app
* **Основной канал:** **Kafka** (асинхронное взаимодействие). Классический REST не подходит, так как бизнес-требования ожидают отображения предложений пользователю по мере их поступления, а не после сбора абсолютно всех ответов.
* **REST эндпоинты:** Используются исключительно как сервисные: `/health`, `/ready`, `/metrics`, `/admin/*`.

## 2. Интеграция core-app ↔ osago-aggregator
Взаимодействие строится на базе **Kafka (Event-Streaming)**:
1. `core-app` → отправляет событие в топик `osago.application.created` *(одно событие на заявку)*.
2. `osago-aggregator` (consumer group) → считывает событие, веером рассылает запросы в страховые компании и начинает опрос.
3. `osago-aggregator` → отправляет события в топик `osago.offer.received` *(по одному событию на каждую страховую — строго по мере прихода ответов)*.
4. `core-app` (consumer group) → получает эти события и моментально пушит их конечному пользователю.

**Что это даёт:** Полное отсутствие каскадных отказов. Сбой в одной страховой компании никак не блокирует обработку остальных. Создается надежный буфер на 60 секунд времени ожидания и на пиковые 2 500 пользователей.

---

## 3. API для веб-приложения
* `POST /api/v1/osago/applications` — создать заявку **(REST)**.
* `GET /api/v1/osago/applications/{id}/offers` — стрим поступающих предложений **(SSE-стрим)**.
* `GET /api/v1/osago/applications/{id}` — получение финального состояния заявки **(REST)**.

---

## 4. Интеграция Web ↔ core-app
* **REST** — применяется исключительно для команд (создание заявки, запрос финального статуса).
* **SSE (Server-Sent Events)** — применяется для стриминга предложений в реальном времени. Это архитектурно проще, чем WebSocket: протокол однонаправленный, работает поверх HTTP/1.1 и поддерживает автоматическое переподключение (auto-reconnect) на стороне браузера.

---

## 5. Паттерны отказоустойчивости

| Паттерн | Где применяется | Параметры и логика работы |
| :--- | :--- | :--- |
| **Rate Limiting** | API Gateway (inbound, per user) | 50 RPS на партнёра, 5 RPS на одного пользователя |
| **Rate Limiting** | osago-aggregator → страховые (outbound, per-insurer) | 20 RPS (согласно лимитам по договору) |
| **Timeout** | osago-aggregator → страховая | 60 секунд (согласно техническому заданию) |
| **Retry** | osago-aggregator → страховая | 3 попытки, экспоненциальный backoff (1s / 2s / 4s). Включается **только** для ошибок 5xx и таймаутов |
| **Circuit Breaker**| osago-aggregator → страховая (per-insurer) | Состояние `Open` при 50% ошибок за последние 20 запросов. Переход в `Half-open` через 30 секунд |

## 6. Влияние нескольких реплик на архитектуру
При масштабировании системы на несколько подов (реплик) применяются следующие решения:

* **Партиционирование в Kafka:** Настраивается по ключу `application_id`. Благодаря этому все события, относящиеся к одной конкретной заявке, гарантированно попадают в одну партицию и обрабатываются строго одним подом `osago-aggregator`. Это полностью исключает состояние гонки (race conditions) при опросе.
* **Вынос состояния:** Всё состояние хранится в базе данных PostgreSQL, а не в оперативной памяти подов. При падении или перезапуске любой другой под может подхватить и продолжить процесс опроса страховой.
* **Распределённый планировщик:** Опрос полей по времени `next_poll_at` координируется на уровне БД с помощью конструкции `SELECT ... FOR UPDATE SKIP LOCKED`.
* **Consumer group у core-app:** Так как SSE-подписка удерживает постоянное соединение, конкретный под `core-app` должен знать, к кому именно подключен пользователь. Вместо настройки *sticky sessions* на уровне Ingress, выбирается более надёжное решение — **Redis Pub/Sub** для бродкаста (трансляции) ответа на все поды `core-app`.
